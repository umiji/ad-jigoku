# TASK-024B — 面白さゲート（プレイテスト実施・判定）

- Milestone: M4 / Phase 1
- Depends on: 024, 024A
- Size: 1 session（ただしコードなし。プレイテストの実施と判定が成果物）

> **v0.2 新規（`DECISIONS_v0.2.md` §7 全体、D7）**: **M4 完了を「面白さゲート」にする。**
> 通過しなければ M5/M6 に進まない。このタスクは実装ではなく、プレイテストの実施と判定の記録である。

## Objective

「遊ぶ → 結果 → もう一回」が初めて成立する地点（TASK-024 完了時点）で、実際に第三者に
プレイしてもらい、GAME_REQUIREMENTS が要求する「面白さ」を検証する。

## Context

`DECISIONS_v0.2.md §7`。根拠: `GAME_REQUIREMENTS.md §25` Phase 1 の目的は「本当に面白いか検証」。
同 §1.1「UX 検証ツールをゲームと呼んではいけない」。**このゲートを飛ばして M5/M6 に進むことは
CLAUDE.md の方針（設計と実装が矛盾したら黙って無視しない）に反する。**

## Scope（コードではなくプロセス）

1. **手順**: 5人以上に、事前説明なしでプレイしてもらう
2. 計測項目: `GAME_REQUIREMENTS.md §24` Fun 節の5項目 + **2回目プレイ率**
   - 30秒以内に基本目的を理解できるか
   - マニュアルなしで最低1ステージをクリアできるか
   - 失敗時に「何にやられたか」を明確に理解できるか
   - リスタートがほぼ即座か
   - 2回目のプレイが1回目と有意に異なるか
3. **通過条件**（初期値。Q2 でオーナーが最終決定）:
   - 2回目プレイ率 ≥ 60%
   - 「何のゲームか」を30秒以内に言語化できる
4. **不通過時**: M5/M6 に進まない。テンプレート（TASK-008）・threat 値（TASK-009）・
   friction 値（`EngineTuning`。Q1）の調整に戻る。設計変更が要るなら `docs/design/` を
   直す提案を先に出す（CLAUDE.md §3 と同じ原則）

## Key requirements

- プレイテストの記録（誰が・いつ・どの環境で・結果）を残す
- 通過/不通過の判定根拠を数値で残す（感想ベースで済ませない）
- 不通過だった場合、次に何を調整するかを具体的に記録する（次セッションが迷わないため）

## Acceptance criteria

- [ ] 5人以上のプレイテストが実施され、記録が残っている
- [ ] 2回目プレイ率と Fun 節5項目の結果が数値・具体例つきで記録されている
- [ ] 通過/不通過の判定が明記されている
- [ ] 不通過の場合、調整対象（テンプレート/threat/friction のどれか）が具体的に特定されている

## Definition of Done

- 通過と判定された場合のみ、`docs/tasks/README.md` の M4 完了条件を満たしたとみなし、
  M5（TASK-029〜）に進んでよい
- 不通過の場合、本タスクは再オープンされ、調整後に再度プレイテストを実施する
