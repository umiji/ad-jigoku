# ADR-013: 広告のリアリティを実測から作り、中身を後から本物に差し替えられるようにする

- Status: **Proposed（オーナー承認待ち。2026-09-14）**
- Date: 2026-09-14
- Drivers: 2026-09-14 の試遊フィードバック（`docs/reviews/2026-09-14-trial-feedback.md` F-1）

## Context

M2 完了時点の試遊で、オーナーから次の指摘を受けた。

> 広告のリアルさもない。広告のリアルさとは広告の内容ではなく、広告表示のデザイン。
> Close ボタンの作り込みとか、広告ウインドウのデザインとか、もっと各パターンの広告デザインを
> 実際のサイトからベンチマークして作り込む必要はある。

現状のシェル実装は `DESIGN.md §8` の anatomy を満たしているだけで、実物の観察に基づいていない。
「広告っぽい何か」にとどまっており、批評としての説得力を欠く。

さらにオーナーから「実際の広告でやりたい」という要望が出た。これは既存の要件と衝突する。

- `GAME_REQUIREMENTS.md §2`: *Actual deceptive advertisements must never be deployed as part of
  the game. All hostile ad behavior is simulated locally.*
- `SAFE-13`（ADR-012）: ゲーム / LP ルートに実広告ネットワークのスクリプトが存在しない

この記述は 2026-09-12 の初回要件取り込み時点から存在するが、オーナーが意識して決めたものではない
（本人の申告）。よって**改訂可能な前提**として扱う。

### 実広告をゲームに入れた場合の制約（事実確認）

1. **エンジンが成立しない。** 現行エンジンは決定論的（同一シード → 同一展開）で、リプレイを回帰
   テストに使い、「広告がいつ閉じられる状態になったか」を engine が知っていることを前提に採点する。
   実広告はクロスオリジンの枠に毎回異なるものが届くため、engine は状態を知りようがない。
2. **無効トラフィック。** 広告への操作がゲームの目的である配置は、主要ネットワークの規約が禁じる。
   発生するクリックは無効クリックとなり、アカウント停止と収益巻き戻しのリスクがある。
3. **配信承認の不確実性。** そもそも審査に通る保証がなく、時間もかかる。

### オーナーの方針（2026-09-14）

> どうせ広告許可とるまでは時間かかるとおもうし、許可出るかもわからないから、
> まずは実物を観測、再現しながら、将来的に本物の広告を使ってゲームをできることが
> 見えてきたら簡単に本物の広告に切り替えられるような設計にしてほしい。

## Decision（提案）

### D1. 「器」と「中身」を分離し、中身だけを差し替え可能にする

広告を 2 層に分ける。**この境界が、本物への切替口になる。**

```text
器（Shell）  : 枠・ラベル・閉じるボタン・ライフサイクル・重なり順・サイズ
               → 常に自前実装。engine が完全に制御する。差し替えない
中身（Creative）: 器の内側に入る表示物
               → provider: 'simulated' | 'network' で差し替え可能
```

**この分け方なら、中身が本物になってもエンジンは壊れない。**

- 閉じるボタンは常にこちらのものなので、SAFE-01（必ず閉じられる）は provider に依存せず成立する
- engine は creative の中身を一切参照しない（すでに現行もそうなっている）ため、決定論とリプレイは
  provider に依存せず成立する
- threat / patience / 採点は Shell とパターン定義から決まるため、provider に依存しない

### D2. リアリティの出典を「実測値」に一本化する

シェルの見た目を、実物の観測から得た数値で定義する。新規文書 `docs/design/AD_ANATOMY.md` を
**シェル実装の唯一の出典**とする。記録する項目（最低限）:

- 閉じるボタン: 実寸 px・枠の内か外か・コントラスト・出現から押下可能までの遅延
- 広告枠: 規格サイズ・枠線/影の有無・ラベル（PR / 広告 / Sponsored）の出方と大きさ
- 重なり順と、本文に対する被さり方
- 読み込み遅延による本文のずれ幅（レイアウトシフト）
- 動画: スキップ可能になるまでの秒数

**観測方法は 2 系統。**

1. **公開仕様**（配信タグのドキュメント、IAB の規格サイズ、動画広告規格のスキップ規定）
2. **自前の観測ページ / 実サイト計測**。TASK-038 以降の Probe runner がこの計測器そのものなので、
   **監査機能の実装を前倒しして、ゲームの作り込みに再利用する**

**持ち帰るのは数値とスクリーンショットのみ。実物の CSS / JS / クリエイティブは複製しない**
（著作権・商標、および実物のスクリプトは計測ビーコンを飛ばすため）。

### D3. 要件を改訂する（オーナー承認が必要）

`GAME_REQUIREMENTS.md §2` の該当記述を、次の趣旨に改める提案。

| 現行 | 改訂案 |
|---|---|
| Actual deceptive advertisements must never be deployed as part of the game. | ゲーム内の広告は、既定では自前クリエイティブとする。実配信クリエイティブへの差し替えは、配信承認とポリシー適合が確認できた場合に限り、`provider: 'network'` により可能とする |
| All hostile ad behavior is simulated locally. | **加害的な「挙動」は常にローカルで模擬する**（閉じられなさ・再出現・誤タップ誘発は engine が制御する）。実配信に委ねるのは表示物のみ |
| The MVP is NOT ... a game whose primary mechanic is repeatedly clicking tiny close buttons | （F-4 ゲームルール検討と併せて再検討。現行実装はこの禁止に抵触している疑いがある） |

SAFE-13 は**廃止しない**。「ゲーム/LP に実広告ネットワークのスクリプトが存在しない」を、
当面の既定値として維持する。解除は D1 の継ぎ目を通してのみ行えるようにし、解除条件を明文化する。

## Consequences

### 良い

- 本物に切り替えられなくても（承認が下りなくても）、リアリティは実測値から得られる
- 切替が来たときの変更範囲が creative 層に閉じる。engine・採点・テストは無改修
- 「加害的な挙動は常に自前」なので、批判対象と同じ行為をしていないことは構造で保証され続ける

### 悪い

- 観測作業が先行コストとして乗る。Probe runner の前倒しが必要
- `AD_ANATOMY.md` という新たな出典が増え、DESIGN.md との整合を取る手間が生じる

### オーナー裁定（2026-09-14）

**Q1（実広告クリックの無効トラフィック問題）: 保留。** 当面は実広告を入れないため、判断を先送りする。
`provider: 'network'` の解禁条件（旧 Q2）も同時に保留。

**代わりに、模擬広告のクリック/タップ時のギミックを決定した。**

> 模擬広告の場合は広告をクリック、タップしたときに違うブラウザが立ち上がるギミックにしておこう。

これは実際の広告 UX（タップすると新しいタブ/ウインドウ/ストアに飛ばされる）の再現であり、
リアリティ強化の中核になる。ただし**実装は完全に偽物でなければならない**:

| 制約 | 理由 |
|---|---|
| 実際の `window.open` / 外部遷移 / 履歴操作を**行わない** | SAFE-04/09/10。自分がやったら終わり |
| 偽ウインドウは自前 viewport の内側に描画する | 同上 |
| 実ブラウザの外装を模倣しない。実在ドメインを表示しない | SAFE-12 |
| 偽ウインドウも `MAX_CLOSE_DELAY_MS` 内に必ず閉じられる | SAFE-01 |
| フォーカストラップを作らない。`aria-label` は常に真の動作を述べる | SAFE-02、支援技術に嘘をつかない |

**カタログ上の扱い（要判断）**: 現行カタログ（A〜K の 92 件）に「クリックすると別ウインドウが開く」
に対応するパターン ID は**存在しない**。二択:

1. **パターンではなく「誤タップの結果（outcome）」として実装する。** カタログ改訂が不要。
   `engine/intent.ts` の outcome テーブルに追加する
2. **カタログに新規パターンとして追加する。** 採点対象になる。ADR-001 により
   `AD_UX_PATTERN_CATALOG.md`（Markdown）への追記が先

**Q3（ゲームルール）: 「小さな閉じるボタンの連打を主機構にしない」は厳守しない。**

> 広告パターン 90 種類用意しているのであればこの閉じるボタン連打にならないようなゲームステージ
> 設計はできるのでは。また、閉じるボタンの連打でも閉じるボタンの表示方法が全て異なるなど
> 難易度設計で変わる部分もあると思うのでここのルールは厳守しなくてもいい。

よって `GAME_REQUIREMENTS.md §2` のこの行は**禁止事項から設計指針へ格下げ**する（TASK-052 で改訂）。
単調さはステージ構成と閉じるボタンの表現差で解消する方針とする。

### オーナー裁定 第2回（2026-09-14）

- **偽ウインドウは「完全に偽物」で確定。** 上表の制約をそのまま実装条件とする
- **MVP のパターンは 15 件のまま維持**（Q5 は解消）。オーナー: 「MVP は 15 個でいい。今後増やす
  場合はさっき言ったような考え方でやってほしい」= 増やすときは、単調さをステージ構成と
  閉じるボタンの表現差で解消する方針を前提にする
- **偽ブラウザのタブ表示は残す**（Q6 は解消）。F-3「タブは要らない」は撤回。よって
  「別ブラウザが立ち上がる」ギミックの作用先が確保される

### オーナー裁定 第3回（2026-09-14）

**「別ウインドウが開く」は outcome として実装し、得点は与えない**（Q4 解消）。
オーナー: 「タブが開いたことに対する対処は得点として与えないでいい」。

- カタログへのパターン追加は不要（ADR-001 の改訂も不要）
- 押し間違えた結果としての罰。偽ウインドウを閉じる手間は我慢メーターの消耗としてのみ効く
- 実装先は誤タップの結果テーブル（TASK-054 の範囲）
