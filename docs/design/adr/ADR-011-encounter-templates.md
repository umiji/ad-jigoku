# ADR-011: エンカウンターテンプレートと合成妥当性ルールによるステージ生成

- Status: Accepted
- Date: 2026-09-12
- Drivers: D1, D4（`DECISIONS_v0.2.md` §3, §4 C1/C2）

## Context

v0.1 のステージ生成器は「候補から k 個ランダムに抽選」するだけだった。これは無数のバリエーションを
作れるが面白さを保証しない。純粋ランダムの組み合わせは手作り15ステージより体験が劣る、というのは
ローグライク開発における既知の教訓である。加えて、個々のパターンが公平でも組み合わせは不公平に
なり得る（例: moving + tiny + delayed の close 摩擦が同時に乗ると物理的に不可能な難易度になる）が、
v0.1 の生成器はこれを検査していなかった。

## Decision

ステージを**エンカウンターテンプレート**（役割スロットの列: interrupt/trap/pressure/wildcard/finale）
で構造化し、生成器が役割ごとにカタログから埋める。物語ステージはテンプレートを固く（同じ
「起承転結」で中身だけ変える）、Endless は緩くする。

生成時に以下の合成妥当性ルール R1〜R8 を全チェックする:

- R1 スロット排他、R2 シェル互換、R3 ペア非互換（既存 `incompatibleWith`）
- **R4 摩擦上限**・**R5 認知負荷予算**（v0.1 になかった新規ルール）
- R6 SAFE-01、R7 難易度帯（棄却して再抽選）、R8 frame 要件

さらに、カタログへのパターン追加で過去の共有 seed が壊れないよう、配列インデックス抽選ではなく
**rendezvous (HRW) hashing** で候補を選ぶ。`w = hash(seed, stream, patternId)` の上位 k を採用する。

## Consequences

### 良い

- 「無数に作れる」と「どれを引いても面白い」を両立させる設計上の投資になる
- R4/R5 により、個々に公平なパターンの組み合わせが理不尽にならないことを構造的に保証する
- rendezvous hashing により、カタログ更新後も既存 Seed Challenge の大半が保存される

### 悪い

- R4 の `FRICTION_CAP` / R5 の `LOAD_BUDGET` の初期値は勘であり、実測データがない（Q1）
- テンプレート設計そのものの質に面白さが依存する。設計が悪ければ「構造化されたつまらなさ」になり得る
- 全組み合わせのテストは依然として不可能（fast-check の property test で代替）

### 緩和

- Q1 は TASK-008 実装時に仮置きし、面白さゲート（GAME §7）のプレイテストで調整する
- 理不尽な組み合わせの発見はプレイテストに委ね、`incompatibleWith` と `friction` 値に還元する運用にする
